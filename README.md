# stockbot — дайджест остатков и потребности в закупке

Бот присылает в Telegram сводку по **доступному остатку** и плановому заказу
**каждую среду в 10:00**, считая **следующую неделю (пн–вс)**: общая картина,
затем отдельным сообщением на каждого поставщика — с количеством, ссылками на
карточки Wildberries и возможностью создать черновик заказа в МойСклад.

## Модель планирования

```
Среда 10:00  →  расчёт  →  окно: следующий понедельник – воскресенье
                              ↑
                    3 дня на проверку наличия у поставщика,
                    формирование закупки и доставку до склада
```

Ключевое отличие от «сколько продадим за 7 дней от сегодня»:

| Что | Как считается |
|---|---|
| Окно покрытия | Следующая неделя пн–вс, а не 7 дней от даты запуска |
| Буфер пополнения | `replenishment.handling_days: 3` — от решения до товара на складе |
| База потребности | Остаток **к началу окна**, а не сегодняшний |
| Упущенные продажи | Только внутри окна: что теряется на текущей неделе, закупкой уже не исправить |

Если запустить вручную в понедельник, окно всё равно начнётся через неделю.
Иначе расчёт покрывал бы уже начавшуюся неделю.

Остаток к началу окна считается симуляцией по дням: из доступного остатка
вычитается спрос за `дни_до_старта`, прибавляются поступления с учётом их ETA.
Иначе товар, который продастся до понедельника, посчитается дважды —
и заказ окажется завышен.

### Срок поставки важнее буфера

`handling_days: 3` — это буфер на процедуру. Реальный срок пополнения задаётся
**на поставщика**:

```yaml
suppliers:
  "ООО Текстиль-Опт":
    lead_time_days: 3        # со склада в Москве
  "Marmaris Textile":
    lead_time_days: 12       # импорт
```

Если срок больше, чем дней до начала окна, позиция помечается
`⏳ Не успевает к началу окна` — и это правда, которую лучше видеть.
Срок размещения заказа считается от самого медленного поставщика среди
позиций к заказу.

## Что взято из отчёта МойСклад «Управление закупками»

| Из отчёта | Как используется |
|---|---|
| Поля Остаток, Резерв, Ожидание, Доступно, Дней запаса, Заказать | Те же названия в сообщениях и CSV |
| Доступно = Остаток − Резерв | База расчёта |
| Заказать = Запас − Доступно | Логика потребности |
| Создание заказа поставщику из отчёта | `/order <поставщик>` создаёт черновик |

## Что исправлено относительно отчёта

| Проблема отчёта | Решение |
|---|---|
| «Продаж в день» = Кол-во ÷ календарные дни | Деление на **дни фактического наличия** |
| «Ожидание» вычитается целиком, без даты | Симуляция по дням, поступления **по ETA** |
| Нет страхового запаса | `z × σ × √7`, z = 1.65 |
| Нет сезонности | Коэффициенты по категориям + профиль дня недели |
| Нет MOQ | Округление вверх до упаковки |
| Заказ не ограничен концом сезона | Закупка вне сезона обнуляется |

## Учёт по одному складу

```yaml
warehouse: "Основной склад"
```

При нескольких складах `/report/stock/all/current` даёт **сумму по всем**,
и резерв основного смешивается с остальными. Поэтому используется
`/report/stock/bystore` с фильтром по id нужной точки. Отгрузки, резерв
из заказов и поступления фильтруются по тому же складу.

Если под имя подходит несколько складов, бот скажет и перечислит доступные,
а не выберет молча.

## Сопоставление с Wildberries по баркоду

```
МойСклад: barcodes модификации — ean13 / gtin / ean8
        ↓ нормализация: только цифры, ведущие нули отброшены
WB: sizes[].skus[] — ОСНОВНОЙ и ДОПОЛНИТЕЛЬНЫЙ баркод размера
        ↓
nmID → https://www.wildberries.ru/catalog/{nmID}/detail.aspx
```

Два момента, на которых это обычно ломается:

**Нормализация обязательна.** EAN-13 и GTIN-14 одного товара отличаются
ведущим нулём. Без сведения к общему виду сопоставление молча не сходится —
часть позиций просто останется без ссылок, и вы этого не заметите.

**У размера может быть два баркода.** WB отдаёт в `skus[]` и основной,
и дополнительный. Проверяются все: совпадение по любому даёт карточку.
Ищется по всем вариантам записи — с нулями и без, до 13 и 14 знаков.

Сопоставление идёт **на уровне баркода, а не карточки**: у одного `nmID`
несколько размеров, у каждого свой баркод. Матчинг по карточке выдал бы
всем размерам одну ссылку — для закупки это неверно.

### Кэш

Полная выгрузка карточек — десятки запросов с лимитами 429. Индекс баркодов
кэшируется в файл на 12 часов; недельный дайджест не выгружает всё заново.

### Если карточка не найдена

Ссылка на поиск по артикулу с пометкой `WB?` — чтобы нельзя было спутать
с точной карточкой. Отключается через `wildberries.search_fallback: false`.

## Структура

```
config.yaml            склад, окно, буфер, поставщики, WB, MOQ
main.py                dry-run и run
src/ms_client.py       API МойСклад: остатки по складу, баркоды, ETA поступлений
src/wb_client.py       WB Content API: курсорная пагинация, индекс баркодов, кэш
src/pipeline.py        сборка строк: доступно + в пути + баркоды → ссылки
src/calc.py            ядро: календарь окна, симуляция, потребность
src/render.py          сводка, разбивка по поставщикам, CSV
src/orders.py          создание черновика «Заказа поставщику»
src/bot.py             aiogram: /digest, /supplier, /order, /why
tools/make_mock.py     демо-выгрузка с баркодами
tools/make_wb_index.py тестовый индекс WB для офлайн-проверки
```

## С чего начать

Пошаговая инструкция по бесплатному развёртыванию — **[INSTRUKCIYA.md](INSTRUKCIYA.md)**.

Кратко:

```bash
python main.py dry-run      # проверить расчёт на своих данных

```

## Запуск

Токены — только в переменных окружения, не в коде и не в переписке.

```bash
export MOYSKLAD_TOKEN='...'      # Настройки → Приложения
export WB_TOKEN='...'            # Кабинет WB → Доступ к API, категория «Контент»
export TELEGRAM_BOT_TOKEN='...'  # @BotFather
export TELEGRAM_CHAT_IDS='123456789,-1001234567890'

python main.py dry-run           # проверка на живых данных
python main.py run               # бот + среда 10:00
```

WB-токену нужна категория **«Контент»**. Без неё будет 403.

## Команды бота

| Команда | Что делает |
|---|---|
| `/digest` | сводка + сообщение по каждому поставщику + CSV |
| `/supplier Текстиль` | только один поставщик |
| `/order Marmaris` | черновик заказа поставщику |
| `/order all` | черновики по всем поставщикам |
| `/why WO-OSLO-M` | разбор расчёта и сопоставление с WB |
| `/reload` | пересчитать |

Заказ создаётся **непроведённым**, с плановой датой поставки = начало окна.
Проверяет и проводит человек.

## Что попадает в дайджест

Считаются все SKU, показываются — только те, по которым нужно решение.

```
3 000 SKU просмотрено  →  ~90 позиций в закупку
```

| Куда | Что попадает |
|---|---|
| Сообщения в чат | Только позиции с потребностью > 0, по поставщикам |
| CSV | То же самое — только позиции к заказу |
| Сводка | Воронка: сколько просмотрено, сколько в закупку |

Позиции «достаточно запаса», «сезон закрыт» и «без движения» в выгрузку
**не попадают**: они не требуют действия и на объёме 3000 SKU дают
~2950 строк шума, в которых теряется то, что реально надо заказать.

Если полная картина всё-таки нужна для аналитики:

```bash
python main.py dry-run --csv-all --csv full.csv
```

Колонки CSV: `Остаток к началу недели`, `Спрос за неделю`, `Упущено за неделю`,
`Срок поставки, дн`, `Успевает к окну`, `Баркод (EAN/GTIN)`,
`WB совпадение` (`карточка` / `поиск` / пусто), `WB ссылка`.

## Что настроить под себя

- `warehouse` — имя склада
- `replenishment.handling_days` — буфер на процедуру пополнения
- `suppliers.*.lead_time_days` — реальный срок от каждого поставщика
- `seasonality` — заменить расчётом из истории за 2–3 года
- `dow_profile` — профиль дня недели
- `wildberries.cache_ttl_minutes` — частота обновления индекса баркодов
- `schedule` — день и время рассылки

## Известные ограничения

1. **Дни в наличии** — приближённо, по датам приходов. Точный вариант — ежедневный снимок остатков:

   ```sql
   CREATE TABLE stock_snapshot (
     snap_date date, sku_id text, stock numeric, reserve numeric,
     PRIMARY KEY (snap_date, sku_id)
   );
   ```

2. **Баркоды должны быть заполнены в МойСклад.** Без `ean13`/`gtin` сопоставление невозможно — останется только поиск по артикулу. В `/why` это видно явно.
3. **Один баркод — одна карточка.** Дубли на WB — ошибка данных, берётся первое совпадение.
4. **Комплекты (bundle)** не уменьшают остаток компонентов — потребность нужно разворачивать в `pipeline.py`.
5. **Новинки** без истории дают темп 0; прогноз задаётся через `fixed_daily`.
